# 面试学习笔记

这个文件持续记录项目中值得理解和讲述的设计。不要只背结论，要能结合
代码和测试解释。

## 为什么选择 Django

Django 内置 ORM、表单校验、鉴权、CSRF 和管理后台。对于单人维护的业务
应用，它减少了自行拼装安全基础设施的风险。

## 为什么选择模块化单体

InternFlow 当前没有独立扩缩容或跨团队交付的需求。单体能保持一次请求、
一次事务和一套部署流程。模块边界仍然保留，未来可以按真实压力拆分。

## 为什么本地使用 SQLite、生产使用 PostgreSQL

SQLite 让贡献者零配置启动；PostgreSQL 提供更符合线上服务的并发能力和
运维生态。Django ORM 与测试确保两种数据库共享主要业务行为。

## 所有权隔离

“用户已登录”不等于“用户有权访问这条数据”。每个详情、编辑、删除和
状态更新查询都必须同时匹配对象 ID 与当前用户，测试中需要构造第二个
用户验证越权访问失败。

## HTMX 的渐进增强

筛选请求带有 `HX-Request` 时只返回工作台局部模板，普通请求返回完整页面。
状态更新仍然使用普通 HTML 表单，所以 CDN 不可用或浏览器禁用 JavaScript
时，核心流程不会中断。

## 状态变更的事务边界

快捷更新使用 `transaction.atomic` 和 `select_for_update`。读取当前状态、
写入新状态和追加历史记录属于同一个事务，避免并发请求造成状态与历史
不一致。

## 数据库索引

看板最常见的查询条件是“当前用户 + 进度”，截止提醒是“当前用户 +
截止日期”，因此模型为这两组字段建立联合索引。索引来自实际读取路径，
而不是为每一列盲目添加。

## CSRF 与请求方法

Django 表单都携带 CSRF token。状态更新和删除只通过 POST 修改数据；
无效状态返回 400，访问其他用户的记录返回 404，减少对象是否存在的信息
泄漏。

## 可复现构建

`uv.lock` 固定 Python 依赖，Docker 镜像按 lock 文件安装生产依赖，CI 使用
同一套命令执行格式、静态检查、测试、迁移检查和镜像构建。这样本地、
CI 与容器之间的差异更小。

## 为什么首版简历分析不用外部大模型

简历包含联系方式、教育经历和工作经历，默认发送到第三方会扩大隐私边界。
v0.2 使用本地、确定性的规则检查结构、量化成果、行动动词和技术关键词。
它的结论可解释、可测试、没有调用成本，也不会因为模型升级产生结果漂移。
未来若增加模型分析，必须由用户明确开启，并保留本地模式。

## 文件上传安全

不能只相信浏览器的 `accept` 属性。服务端同时检查扩展名、MIME 类型和
5 MB 大小限制；存储路径忽略用户文件名并使用随机 UUID。解析失败不会
创建简历记录，替换和删除简历时也会同步清理旧文件。

## 清单重新生成为什么保留完成状态

直接删除重建会让用户失去已经完成的进度。服务先记录已完成任务的标题，
生成新清单后对同名任务恢复状态。岗位要求发生变化时，新任务会出现，
已经完成且仍然相关的准备不会丢失。
